1. My reading of the MVP

Ships in MVP (self-serve)
  • Cognito accounts · church Owner/Editor
  • Guided onboarding (easy, no experience)
  • 4–6 faith templates · logo → colors
  • Church pages: About, Pastor, Ministries, Events…
  • Easy Button (AI scrape) · readiness checklist · preview
  • Amplify publish · subdomain + CNAME
  • Stripe monthly tiers · SES email · support chatbot (platform only)
  • Basic analytics · AI images with quotas
Explicitly later / TBD
  • Prospect Studio / sales pre-builds at scale
  • Own giving processor (Stripe Connect long-term)
  • Contact & prayer forms (Phase II)
  • Google Maps embed · church public chatbot
  • White-label / affiliates
  • Full custom “Hollo-style” AI site = highest tier idea

One sentence

Faithocity MVP = an easy, church-specific website builder that smaller churches can launch themselves — AI-assisted, Amplify-hosted — as the first brick of a larger church ecosystem.

What live church samples taught me (reference only)

2cal.org · centralbaptist · rayofhope · csmbc — custom WP, richer than MVP. Patterns: Watch Live / Give / Events / Pastor / Ministries. MVP keeps these as simple modules.

How this changes my plan

  • MVP templates should share one section system (hero, icon rail, mission, messages/sermons, events, CTA band, footer) with theme tokens (colors, fonts, photo mood) — matches these three variants.
  • Target look is high-end but simpler than custom WP — still: Plan a Visit, Watch/Sermons, Events, Ministries, About.
  • Footer credit “Powered by The Church Online” is already in the comps — keep as platform brand on published sites.
  • POC updated to use these three names/palettes as selectable templates.

Step 4 of 7

4. Suggested stack

Named by leadership (locked direction)
  • Auth: AWS Cognito
  • Hosting sites: AWS Amplify
  • Email: AWS SES
  • Domains: Route 53 (explore)
  • Payments: likely Stripe
  • Support AI: ChatGPT + our knowledge docs
  • AWS sub-account for cost isolation
My recommendation (fits our team)
  • App: Next.js + TypeScript
  • API: NestJS or Next route handlers
  • DB: PostgreSQL (tenant_id everywhere)
  • Cache/jobs: Redis + queue for scrape/AI
  • Media: S3 + image pipeline (WebP, crop, size caps)
  • Integrations: Google Calendar, YouTube embeds, Maps links
  • URL model: church.faithocity.com wildcard (CNAME-safe)

Why Next.js: JC/CJ frontend strength + my Nest/Node background; SSR for public church pages; one repo for builder + marketing.

Step 6 of 7

6. What I’d POC first (before betting MVP)

  1. Easy Button mapper — scrape 3 real church URLs → structured JSON (name, pastor, times, ministries) → drop into one template. Measure junk rate.
  2. Publish pipeline — Cognito user → site record → Amplify/static deploy → *.faithocity.com preview.
  3. Guided wizard UX — click-through only (see accompanying HTML POC) proving “no experience required.”
  4. Image pipeline — upload 10MB photo → WebP web sizes; reject/limit abuse.
  5. Stripe subscription skeleton — Starter checkout + webhook → feature flags.
